| Video | `machine = svga_s3`, `memsize = 16`, `aspect = true`, `output = opengl`, windowed (Alt+Enter for fullscreen) |

| Sound Blaster | `sbtype = sb16, sbbase = 220, irq = 7, dma = 1, hdma = 5` |
| MIDI | `mpu401 = intelligent`, `mididevice = none` |

**Why IRQ 7, not the GOG config's IRQ 5:** the MEL audio library verifies
the configured SB IRQ by firing a test interrupt after the DSP handshake
(docs/known-bugs.md 2.6), and **the SOUND.CFG our rig stages records IRQ 7**
(it was captured by a real `sound_ds.exe` run under a conf with IRQ 7; the
`07 00` field is visible in its hex dump). Pairing that SOUND.CFG with a
GOG-style IRQ 5 conf makes the verify fail and DSUN.EXE self-exits ~2.4 s
after boot (observed 2026-11-20, first launch attempt). The harness config
(`tools/repro/configs/ds1.conf`), which pairs IRQ 7 with this SOUND.CFG, is
the combo proven on this machine, and the facility configs mirror it.
GOG's own IRQ-5 pairing works only inside GOG's patched DOSBox with GOG's
own config files; that statement in known-bugs.md 2.6 refers to GOG's tree,
not to a fixture-SOUND.CFG rig.

**Why `mididevice = none`:** with the fixture SOUND.CFG (MEL configured for
Sound Blaster), MEL must not be pointed at a live MIDI device it cannot
probe ("Mel Fatal Error #25 Trap #16" class, harness config comment). The
MPU-401 intelligent mock stays up; the primary conf's MT-32 ROMs are
inherited but unused by MEL.

## Mounts and the DARKRUN.GFF protection

Every launch uses the layered mount discipline from `tools/repro/`
(build_cmdline in repro.py is the reference):

```
mount c <install>               (read-only base)
mount c <saves-overlay> -t overlay   (every engine write lands here)
imgmount e <install>/game.ins -t iso  (DS2 only: CD data track)
c:   then DSUN.EXE (DS1) / DSUN -W0 -L (DS2)
--exit   (DOSBox closes when the game returns to the DOS prompt)
```

The original engine **zeroes `DARKRUN.GFF` in its own folder on boot if it
can write there** (docs/qa-packet setup step 2; engine-quirks.md entry 4).
The overlay mount makes that impossible: writes land in the overlay, the
patched install stays pristine, and `apply.py --verify` stays green.

DS2 factory saves note: DS2's `__support/save/` also ships `DARKRUN.GFF`
(DS1's does not); the engine copies `DARKSAVE.GFF` -> `DARKRUN.GFF` at
startup, and both games exit if `DARKSAVE.GFF` is missing from C:\.

## SOUND.CFG

Both games need a `SOUND.CFG` at C:\ root; the factory one would put MEL
on a device it cannot probe (Mel Fatal Error). The launcher seeds the
proven configs from the repro fixtures
(`tools/repro/bugs/{ds1,ds2}-smoke/SOUND.CFG`), originally generated by a
real `sound_ds.exe` run selecting Sound Blaster. Copies live in
`.testing_facility/seed/<game>/` so the facility is self-contained.

## Launcher

`darksun` in `~/.zshrc` (added 2026-11-20):

- `darksun` — interactive picker; prints each install's patch identity
  (tool, version, journal status, fix count, read live from
  `darkfix-applied.json`).
- `darksun ds1` / `darksun ds2` — straight in.
- Seeds any missing factory files into the overlay (never clobbers saves),
  then launches DOSBox with the layered mounts above.
- Saves live in `.testing_facility/<game>-saves/`; backup a save set by
  copying `Save*.sav` **plus `DARKRUN.GFF`** out of the overlay (DS2 needs
  DARKRUN restored together with its saves or the party lands outside map
  bounds).

## Rebuilding / reverting

```sh
# toolchain: gff-cat is needed by the applier (GFF chunk fixes)
cargo build -p gff-edit --release          # then export DARKFIX_GFF_CAT=.../target/release/gff-cat
# apply / verify / revert
python3 .testing_facility/ds1-patch/apply.py .testing_facility/ds1-patched --verify
python3 .testing_facility/ds1-patch/apply.py .testing_facility/ds1-patched --unapply
```

dosbox-staging 0.82.2 loads GOG's OGG track remap itself: imgmounting
`game.ins` on E: makes staging pick up `MUSIC/TrackNN.ogg` next to the
mounted image, and the launch log shows all 40 tracks loaded
(`CDROM: Loaded Track02.ogg ... Track41.ogg`, "CDAUDIO: Operating at
22050 Hz"). The redbook-static ear test residual (known-bugs.md 2.5)
can ride this rig: GOG's re-encodes bypass the defective pressings, so
the expected verdict is "no static".
