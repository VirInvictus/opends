## 1. DATA is the DS2 spell system's data file (layout proven, descriptor decode open)

The single biggest coverage gap is smaller than it looked and bigger
in content. The "1292 DATA chunks across 4 files" are 323 unique
chunks in one container shipped four times: DS2's RESOURCE.GFF
lineage (GOG CD `RESOURCE.GFF` and, byte-identical, `RESFLOP.GFF` in
the floppy 1.0, HotU, and cd10 trees; the three archive copies have
identical payload, the GOG 1.10 copy differs by exactly 5 bytes, see
below). 1292 = 4 x 323. No DS1 file carries DATA anywhere in the
corpus; DS1's RESOURCE.GFF instead carries RDAT (45 chunks), its
era's equivalent slot.

All four files carry DATA as a segmented type (runs `[(0,320),
(1000,3)]`, secondary table inside GFFI chunk 16); the per-chunk
(id, location, length) records have never been tabulated before
because format-coverage.py stops at the type list.

Layout (offsets cite `.games/ds2/RESOURCE.GFF`):

- Ids 0..319: exactly 320 records of exactly 73 bytes each, contiguous
  from 73960 (cd10/floppy base 73781; +179 in GOG 1.10).
- Record layout: bytes 0..31 binary descriptor, bytes 32..63 NUL-padded
  32-char long name, bytes 64..72 NUL-padded 9-char short name. All
  320 long names decode as clean ASCII, none empty.
- The names are the DS2 spell list: `ARMOR`, `BURNING HANDS`, `CHARM
  PERSON`, ... in near-alphabetical wizard-1 blocks, cleric and
  psionicist blocks (`PRAYER`, `IRON SKIN`, `ENHANCED STRENGTH`), and
  ids 269..319 = 51 `MONS269`..`MONS319` placeholders (summoned
  monsters carried as spells).
- Ids 1000..1002 are auxiliary tables appended after the interleaved
  TEXT id 1000 (the item/spell description list): id 1000 (320 B) =
  8 rows x 20 LE u16 monotonic-from-0 ramps (read as per-class
  level-up XP tables); id 1001 (576 B) = sparse flags with two
  self-similar halves; id 1002 (168 B) = 21 (u32, u32) pairs reading
  as (XP value, index) with lane 2 = 1 then 50..69.
- Size histogram across the kind: 73 x 320, 168 x 1, 320 x 1, 576 x 1.
  Nothing else exists in any of the four files.

The GOG 1.10 patch, exactly 5 bytes across all 323 chunks: id 155
(`PRAYER`) descriptor byte 1 `0x00 -> 0x14` (20), and id 1000 row 6
two u16 steps `14000 -> 24000`, `17000 -> 27000` (repairs a broken
+3000 progression). This is the official 1.10 RTPatch's data-table
work, visible at the byte level.

Open (documented as open, with confirm/refute tests):

- The 32-byte descriptor is undecoded. Byte 0 histogram {4:87, 5:98,
  6:81, 7:41, ...} smells like a school/level pair; byte 31 is
  bimodal 0xa0/0xa1 with a long tail. Tests: correlate against the
  shipped Cluebook's spell levels/schools; check byte 1 as an
  animation id (PRAYER gaining 20 in 1.10) by decoding SPIN/ICON 20/
  40/160 with image-extract.
- Id 1001's record shape (576 sparse bytes, no clean width; 576 =
  320 + 256 suggests per-spell scatter plus a second block). Test:
  align byte i to spell i for i < 320.
- Id 1002's index lane (1, 50..69) matches neither spell ids nor MONS
  ids. Test: xref the chunk id in DSUN.EXE's secondary-table reader.
- Whether id 1000's 8 rows map to the 8 classes in order is a guess
  until RDAT (DS1) or the engine reader is compared. Rows 3 and 5
  still hold non-monotonic steps in 1.10, so "clean progression" is
  not universal.

What this means for the port: the DS2 spell engine's data surface now
has a known address and shape (320 records + 3 tables), the same in
every release, so a Godot-side spell table can be generated from DATA
directly instead of hand-transcribing the cluebook. docs/spell-catalogue-ds2.md
gains a machine source.

## 2. RBRN is live adaptive-music machinery in DS1 (resolved)

The file-formats.md 5 "needs verification" closes with a full
resolution. Byte-level container evidence on every sequence chunk in
the corpus (83 DS1 + the DS2-lineage copies; structural IFF walks
that close exactly at payload end):

1. **RBRN exists, DS1 only.** 63 RBRN chunks in `.games/ds1/
   RESOURCE.GFF`: one per sequence kind (GSEQ/LSEQ/PSEQ) for each
   track 1..23 except the short cues 7 and 17 (60 + the same counts
   corroborated by whole-file tallies: RBRN=63, TIMB=46, EVNT=70,
   XDIR=70). None in CINE.GFF's four themes, none in CSEQ 1000, and
   none anywhere in DS2 content (floppy RESFLOP.GFF's 36 XMIs are
   TIMB+EVNT only; the GOG build's music is redbook). The DS2-lineage
   engine retains the machinery regardless.
2. **Structure.** First RBRN fully decoded (RESOURCE.GFF GSEQ/1,
   file 0x248ee6): `RBRN` + BE u32 size (26), then LE u16 count (4),
   then count entries of (LE u16 branch id, LE u32 tick): ids
   sequential from 1, ticks strictly increasing 120 Hz positions in
   the EVNT stream. Size = 2 + 6*count on all 63. Endianness is
   forced by the data (BE-first parsing yields nonsense; LE-first
   yields sequential ids in every chunk). TIMB is LE u16 count +
   (patch, bank) pairs.
3. **Playback follows branches.** Every RBRN-carrying track's EVNT
   contains exactly one controller-0x78 (Sequence Branch Index)
   event per RBRN entry, values matching the ids; GSEQ/1 shows the
   pattern: `[BF 78 01]` branch select, `[BF 74 00]` FOR (infinite
   loop), `[B9 73 00]`/`[B9 77 00]` IndirectControl+Callback engine
   polls, `[BF 75 7F]` NEXT wrap. The follower is the engine's Mel
   library ("Mel Real Mode Version 2.0.9b, 08/30/93" at DSUN.EXE
   0x4c76c; `MelBranchTo` / `MelBreakLoopAndBranchTo` /
   `gMelCurrentBranch` / `gMelIndirectControlArray` in the DSO
   symbol dump, `.dso-online/tools/symbols.txt` lines 3459-3550).
   The .ADV drivers and all DS1 sound-stack binaries contain zero
   chunk-name fourccs: Mel parses the forms itself.
4. **Delta-time correction.** file-formats.md 5's "two delta-time
   bytes per event" was wrong for this corpus: delta times are runs
   of < 0x80 bytes summed until the next status byte (zero deltas
   omitted), and note-ons carry note, velocity, then a VLQ duration.
   Clean-parse proof across all 83 DS1 EVNT streams. file-formats.md
   5 is corrected in place.

Prior art and attribution (CREDITS.md row added): Glassmyer's
`.dsun_music/xmi-tool` names the XMIDI controllers (0x73
IndirectControl, 0x74 FOR, 0x75 NEXT, 0x77 Callback, 0x78 Sequence
Branch Index, XmiTool.java lines 106-127), reads the RBRN count
little-endian (lines 230-231), and ships a `--zero-rbrn-count`
repair flag; libgff's bundled `xmi2mid` (ext/xmi2mid.c) defines the
delta encoding (`GetVLQ2`, line 599) and skips every non-EVNT chunk
(`ExtractTracksFromXmi`, line 950), so a straight xmi2mid port
flattens the adaptive loops; the (id, tick) entry decode and the DS1
usage picture above are OpenDS's own, extending Glassmyer's
count-only read.

What this means for the port: a DS1 music director can reproduce the
adaptive behaviour exactly (loop with FOR/NEXT, switch branch index
on combat/state change; the branch points and their ticks are in the
RBRN tables). It also means the future xmi2mid port needs
branch-aware handling or DS1's music degrades to first-branch-only.
Per-track branch counts for audio-cues.md: see the agent table
distilled in file-formats.md 5; tracks 5, 13, 14 branch 7-8 times
(the busiest cues), most tracks 2-6, cues 7/17 and all CINE themes
are linear.
