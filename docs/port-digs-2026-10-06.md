## 1. DATA is the DS2 spell system's data file (layout proven, descriptor decode open)

The single biggest coverage gap is smaller than it looked and bigger
in content. The "1292 DATA chunks across 4 files" are 323 unique
chunks in one container shipped four times: DS2's RESOURCE.GFF
lineage (GOG CD `RESOURCE.GFF` and, byte-identical, `RESFLOP.GFF` in
the floppy 1.0, HotU, and cd10 trees; the three archive copies have
identical payload, the GOG 1.10 copy differs by exactly 5 bytes, see
below). 1292 = 4 x 323. No DS1 file carries DATA anywhere in the
corpus; DS1's RESOURCE.GFF instead carries RDAT (45 chunks), its
era's equivalent slot.

All four files carry DATA as a segmented type (runs `[(0,320),
(1000,3)]`, secondary table inside GFFI chunk 16); the per-chunk
(id, location, length) records have never been tabulated before
because format-coverage.py stops at the type list.

Layout (offsets cite `.games/ds2/RESOURCE.GFF`):

- Ids 0..319: exactly 320 records of exactly 73 bytes each, contiguous
  from 73960 (cd10/floppy base 73781; +179 in GOG 1.10).
- Record layout: bytes 0..31 binary descriptor, bytes 32..63 NUL-padded
  32-char long name, bytes 64..72 NUL-padded 9-char short name. All
  320 long names decode as clean ASCII, none empty.
- The names are the DS2 spell list: `ARMOR`, `BURNING HANDS`, `CHARM
  PERSON`, ... in near-alphabetical wizard-1 blocks, cleric and
  psionicist blocks (`PRAYER`, `IRON SKIN`, `ENHANCED STRENGTH`), and
  ids 269..319 = 51 `MONS269`..`MONS319` placeholders (summoned
  monsters carried as spells).
- Ids 1000..1002 are auxiliary tables appended after the interleaved
  TEXT id 1000 (the item/spell description list): id 1000 (320 B) =
  8 rows x 20 LE u16 monotonic-from-0 ramps (read as per-class
  level-up XP tables); id 1001 (576 B) = sparse flags with two
  self-similar halves; id 1002 (168 B) = 21 (u32, u32) pairs reading
  as (XP value, index) with lane 2 = 1 then 50..69.
- Size histogram across the kind: 73 x 320, 168 x 1, 320 x 1, 576 x 1.
  Nothing else exists in any of the four files.

The GOG 1.10 patch, exactly 5 bytes across all 323 chunks: id 155
(`PRAYER`) descriptor byte 1 `0x00 -> 0x14` (20), and id 1000 row 6
two u16 steps `14000 -> 24000`, `17000 -> 27000` (repairs a broken
+3000 progression). This is the official 1.10 RTPatch's data-table
work, visible at the byte level.

Open (documented as open, with confirm/refute tests):

- The 32-byte descriptor is undecoded. Byte 0 histogram {4:87, 5:98,
  6:81, 7:41, ...} smells like a school/level pair; byte 31 is
  bimodal 0xa0/0xa1 with a long tail. Tests: correlate against the
  shipped Cluebook's spell levels/schools; check byte 1 as an
  animation id (PRAYER gaining 20 in 1.10) by decoding SPIN/ICON 20/
  40/160 with image-extract.
- Id 1001's record shape (576 sparse bytes, no clean width; 576 =
  320 + 256 suggests per-spell scatter plus a second block). Test:
  align byte i to spell i for i < 320.
- Id 1002's index lane (1, 50..69) matches neither spell ids nor MONS
  ids. Test: xref the chunk id in DSUN.EXE's secondary-table reader.
- Whether id 1000's 8 rows map to the 8 classes in order is a guess
  until RDAT (DS1) or the engine reader is compared. Rows 3 and 5
  still hold non-monotonic steps in 1.10, so "clean progression" is
  not universal.

What this means for the port: the DS2 spell engine's data surface now
has a known address and shape (320 records + 3 tables), the same in
every release, so a Godot-side spell table can be generated from DATA
directly instead of hand-transcribing the cluebook. docs/spell-catalogue-ds2.md
gains a machine source.

## 2. RBRN is live adaptive-music machinery in DS1 (resolved)

The file-formats.md 5 "needs verification" closes with a full
resolution. Byte-level container evidence on every sequence chunk in
the corpus (83 DS1 + the DS2-lineage copies; structural IFF walks
that close exactly at payload end):

1. **RBRN exists, DS1 only.** 63 RBRN chunks in `.games/ds1/
   RESOURCE.GFF`: one per sequence kind (GSEQ/LSEQ/PSEQ) for each
   track 1..23 except the short cues 7 and 17 (60 + the same counts
   corroborated by whole-file tallies: RBRN=63, TIMB=46, EVNT=70,
   XDIR=70). None in CINE.GFF's four themes, none in CSEQ 1000, and
   none anywhere in DS2 content (floppy RESFLOP.GFF's 36 XMIs are
   TIMB+EVNT only; the GOG build's music is redbook). The DS2-lineage
   engine retains the machinery regardless.
2. **Structure.** First RBRN fully decoded (RESOURCE.GFF GSEQ/1,
   file 0x248ee6): `RBRN` + BE u32 size (26), then LE u16 count (4),
   then count entries of (LE u16 branch id, LE u32 tick): ids
   sequential from 1, ticks strictly increasing 120 Hz positions in
   the EVNT stream. Size = 2 + 6*count on all 63. Endianness is
   forced by the data (BE-first parsing yields nonsense; LE-first
   yields sequential ids in every chunk). TIMB is LE u16 count +
   (patch, bank) pairs.
3. **Playback follows branches.** Every RBRN-carrying track's EVNT
   contains exactly one controller-0x78 (Sequence Branch Index)
   event per RBRN entry, values matching the ids; GSEQ/1 shows the
   pattern: `[BF 78 01]` branch select, `[BF 74 00]` FOR (infinite
   loop), `[B9 73 00]`/`[B9 77 00]` IndirectControl+Callback engine
   polls, `[BF 75 7F]` NEXT wrap. The follower is the engine's Mel
   library ("Mel Real Mode Version 2.0.9b, 08/30/93" at DSUN.EXE
   0x4c76c; `MelBranchTo` / `MelBreakLoopAndBranchTo` /
   `gMelCurrentBranch` / `gMelIndirectControlArray` in the DSO
   symbol dump, `.dso-online/tools/symbols.txt` lines 3459-3550).
   The .ADV drivers and all DS1 sound-stack binaries contain zero
   chunk-name fourccs: Mel parses the forms itself.
4. **Delta-time correction.** file-formats.md 5's "two delta-time
   bytes per event" was wrong for this corpus: delta times are runs
   of < 0x80 bytes summed until the next status byte (zero deltas
   omitted), and note-ons carry note, velocity, then a VLQ duration.
   Clean-parse proof across all 83 DS1 EVNT streams. file-formats.md
   5 is corrected in place.

Prior art and attribution (CREDITS.md row added): Glassmyer's
`.dsun_music/xmi-tool` names the XMIDI controllers (0x73
IndirectControl, 0x74 FOR, 0x75 NEXT, 0x77 Callback, 0x78 Sequence
Branch Index, XmiTool.java lines 106-127), reads the RBRN count
little-endian (lines 230-231), and ships a `--zero-rbrn-count`
repair flag; libgff's bundled `xmi2mid` (ext/xmi2mid.c) defines the
delta encoding (`GetVLQ2`, line 599) and skips every non-EVNT chunk
(`ExtractTracksFromXmi`, line 950), so a straight xmi2mid port
flattens the adaptive loops; the (id, tick) entry decode and the DS1
usage picture above are OpenDS's own, extending Glassmyer's
count-only read.

What this means for the port: a DS1 music director can reproduce the
adaptive behaviour exactly (loop with FOR/NEXT, switch branch index
on combat/state change; the branch points and their ticks are in the
RBRN tables). It also means the future xmi2mid port needs
branch-aware handling or DS1's music degrades to first-branch-only.
Per-track branch counts for audio-cues.md: see the agent table
distilled in file-formats.md 5; tracks 5, 13, 14 branch 7-8 times
(the busiest cues), most tracks 2-6, cues 7/17 and all CINE themes
are linear.

## 3. The capability permission lists are GPL trigger registrations (resolved)

Mineout Phase B item 2 closes. The "per-creature permission lists"
of port-digs-2026-09-21.md 2 are the six ENTITY-TRIGGER lists of the
engine's shared 13-byte trigger table (the table exploration-flow.md
0 already points at via `DGROUP [0x42cc]:[0x42ce]`), and their
writer is the GPL interpreter's trigger-opcode handlers. Everything
below is DS1 DSUN.EXE, verified with ovr-map + ndisasm (r2's default
MZ mapping reads the overlay area as 0xFF; the dig documents that
trap).

Writers (all resident, segtab record 2, file 0x97D0..0xD669): each
trigger-opcode handler fetches its 3 (UseWith: 4) operands, builds
an 8-byte template at VM:0xFD, and calls a sorted insert:

| opcode | handler | list (GSTATE 0x377e head) | capability bit |
|---|---|---|---|
| 0x4C PickupItem | 0xB90E -> insert 0xCD25 | +0xD | 1 (steal) |
| 0x6E TalkTo | 0xB9EE -> 0xCD25 | +0xF | 4 (talk) |
| 0x65 Attack | 0xB946 -> 0xCD25 | +0x11 | 2 |
| 0x66 Look | 0xB97E -> 0xCD25 | +0x13 | 8 |
| 0x6D Use | 0xB9B6 -> 0xCD25 | +0x15 | 0x10 (give) |
| 0x70 UseWith | 0xBA5A -> 0xCC71 (two-key) | +0x17 | 0x20 |

Plumbing: insert 0xCD25 (single-key, sort key record+4 = creature
id, replace-on-match copies 7 bytes); 0xCC71 (keys +4 then +6);
link-in 0xCFAB writes the head index; 0xCFFF allocates from a
pre-allocated pool through a free list at VM:0x32d (no heap call at
insert time); remove-head 0x9616; conditional flush 0x8ECB (removes
records whose +6 persistence byte is 0, keeps chunk-99
registrations).

Lifecycle:

- Init, once per session: overlay 13 entry[0] -> ovr22 entry[32] ->
  ovr0 entry[0] allocates the table (count*13 far heap), stores the
  only writers of the `[0x42cc]/[0x42ce]` pointer (0x52F4E-0x52F55),
  threads the free list, then runs global script chunk 0x63 (99
  decimal) type 2 (0x52FFD). Chunk 99's trigger registrations carry
  the persistence flag: they survive forever.
- Any GPL run: RunGplScript 0x97D1 -> executor 0x9AC3 stamps the
  current (chunk, type) into MISC+0x12/+0x14 -> dispatch -> handler
  -> insert. Region/dialog/trigger scripts all register transiently.
- Region change: the party-Tport path (ovr22 local 0x857) loads the
  region, remaps record+0 entry offsets from the region's GPLI
  chunk (reconciler ovr21 entry[28]), then calls the flush
  orchestrator 0x8DD0, which empties the tile/box lists entirely and
  strips non-persistent records from the six entity lists. The
  region's own scripts run after that, re-registering what they
  declare.

Record layout (13 bytes): +0 script entry offset (GPLI-remapped at
region load), +2 GPL chunk id, +4 creature id (sort key), +6
second creature id (UseWith) or persistence flag byte (other
lists; 1 = chunk-99 registration), +8/+9 area box w/h, +0xA mode
gate, +0xB next index (0xFFFF ends; doubles as the free-list link).
Head cells are static 0xFFFF words at file 0x3CBE0 (GSTATE record
87). The same table also carries the tile-pair lists (+0x5/+0x7)
and box lists (+0x9/+0xB) via the tile/box trigger handlers
(catalogue entries 0xB7FA/0xB83F/0xB884/0xB8C9; the insert calls
sit 0x36 bytes into each), which corrects exploration-flow.md 0's
old "runtime-installed driver fn ptrs" reading of those cells
(fixed in place). Twelve of this dig's functions are now rows in
tools/ovr-map/syms/ds1.toml.

Port implication: a demo creature gets engine-true steal/talk/give
exactly one way: something registers a trigger record for its
creature id on the right list before the examine window opens.
Port the table as one 13-byte-record array + ten head indices + a
free list; register the persistent baseline at "global script"
time and transient registrations from region scripts, flushing
non-persistent records on region transition in ovr21 entry[24]'s
order (load, remap, flush, then run region scripts). The capability
mask then falls out of the consumer walker at no extra cost: bit 1
= on PickupItem list, 4 = TalkTo, 0x10 = Use, 2/8/0x20 =
Attack/Look/UseWith, and each registration also names the (chunk,
entry) hook to run when the action fires.

## 4. The never-shipped kinds: all 21 closed, and every external file identified

The documented-kinds-never-seen list (21 kinds) closes with a corpus
sweep over both GOG trees (saves included), every archive-org tree,
and every zip member scanned in memory, checking each kind as (a) a
TOC type, (b) a chunk-body or nested IFF marker at a verified
boundary, and (c) a whole-file magic:

- **None of the 21 kinds ever shipped as a GFF chunk kind.**
- Engine-known but never materialized: `FVOC`, `STXT`, `CMAP` exist
  as code constants in DSUN.EXE (`push 'FVOC'` at ds1 232446, `push
  'STXT'` at 429494, and the ILBM reader's `BMHD CMAP BODY` string
  table at 83047). The engine could load them; SSI never shipped
  one.
- `FORM` is real but only as the nested IFF marker inside *SEQ
  payload bodies (XMI; file-formats.md 5). Counted at chunk
  boundaries: 13 CINE + 70 DS1 RESOURCE + 1 DS2 RESOURCE + 36 + 36
  floppy/HotU.
- No trace anywhere (not even an EXE code constant): `BMAP`, `DADV`,
  `DBOX`, `DRV`, `GFRE`, `GTOC`, `MENU`, `MGTL`, `MSEQ`, `OMAP`,
  `POBJ`, `SAVE`, `SBAR`, `SINF`, `SJMP`, `TMAP`, `TXRF`. Every raw
  byte hit was individually explained (Vorbis payload noise, BMP
  body bytes, `MENUS.C` debug strings, `SAVE%.2d.SAV` format
  strings, `CHARSAVE.GFF` inside RTPatch entry tables).
- No `.SAV`, `.XMI`, or `.SEQ` file exists anywhere under `.games/`.
  `dsun2_midi_files.zip` holds 35 standard MIDI files
  (`RESFL000.MID`..`034.MID`, `MThd` magic): third-party exports
  matching the DJ.DAT slot count, flagged as future DS2-music
  comparison material.

This converts file-formats.md's kind table entries for those kinds
from "purpose guesses" into "documented as never shipped in DS1/DS2
material" (the census paragraph now sits at the end of section 1).
Practical consequences: a GFF writer never needs GFRE/GTOC/SBAR/
SJMP/POBJ/SAVE/STXT/TMAP/TXRF/OMAP/MENU/MGTL/MSEQ/BMAP/DBOX/DADV/
DRV/SINF/CMAP for these games, and FVOC support in a reader is
optional (the kind is engine-known but was never used).

External-file identifications (full detail in file-formats.md 4's
measured-identifications subsection): STDPATCH.AD decoded (232-entry
directory + 233 x 14-byte OPL2 timbre blobs, 175 GM timbres; DS1 and
DS2 differ in blob content only); GM1/GM2.BNK are Aria banks for
MIDITSR.EXE, not Roland (file-formats.md's old row corrected);
SSI1.INI/UM200/UM206/UM206A are UltraMID GUS patch tables with
SOUND.BAT selecting by patch-set revision (and GOG's SSI1.INI is the
stale revision); ITEMS.BIN is 234 u16 pairs from one id space
(character-transfer xref, exact semantics open); game.gog is the
MODE2/2352 ISO image (volume `WAKE1_0`, 46,400 sectors, data only);
game.ins maps audio tracks 02..41 to MUSIC/TrackNN.ogg (the mineout
prompt's "Track02-26" was wrong; there are 40 audio tracks);
PATCH.RTP family = RTPatch packages with magic `0x00C82A4B`
(targeting CHARSAVE.GFF on CD, DSUN.EXE on the dk11 disk package;
patch-wake3511's payload.arj is a non-parsing ARJ-signature blob);
the five FLIs are vanilla FLIC 1.x with frame counts 1175/373/575/
284/1398.

## 5. Wave 2: MAP byte-verified, VECT/CMAT/CPAL decoded

The region-adjacent gap kinds closed (evidence from the wave 2
agent, distilled; full offset tables in its report):

- `MAP `: the docs were already correct (file-formats.md RMAP/MAP
  section); this wave byte-verified them across all 60 shipped
  chunks: every cell a valid TILE id of the same file, payload
  identical across GOG/floppy/HotU, zero agreement with the GMAP
  byte or wall index at any offset (independent layer), cd10 ships
  no region GFFs, and the DS2 region loader pushes 'MAP ' at
  0x2b7bc between RMAP and GMAP. The missing-tile fallback never
  fires in shipped DS2 data. Registered in the catalogue 2026-10-06.
- `VECT`: one 1024-byte chunk, id 1, byte-identical in all five
  copies: 256 (i16 x, i16 y) records forming the unit circle at
  radius 256 (k=0 up, clockwise, x = trunc(256 sin), y = -trunc(256
  cos)); 254/256 exact, axis entries k=128/k=192 one short. Both
  engines load it with `push 1; push 'VECT'` (DS1 0x60874, DS2
  0x64c9e). Direction-to-step-delta table for the 256-angle
  convention; movement-vs-aim is open.
- `CMAT`: two DS1-only still containers (ids 200/300, 320x200 and
  318x198) holding a single BMA-codec frame each (the cinematics
  codec), byte-exact walks, zero RLE mismatches. The "material
  matrix" reading the name suggests is dead.
- `CPAL`: format = PAL exactly (evidenced now); content = the
  dedicated palettes of the two CMAT stills (CMAT 200's all-index-1
  background is CPAL 200 entry 1). DS1-only; the engine loads
  CMAT+CPAL in one function (0x56ad5/0x56af2).

Open leads for a future Ghidra pass: the VECT caller (DS1 0x60874)
to pin movement-vs-aim; the CMAT/CPAL loader caller to identify the
two stills; the DS2 region-loader block (0x2b7a0..0x2b7e4) showing
RMAP/MAP/GMAP requested consecutively.

## 6. Armour overlays do not exist (Phase B.1 closed as a negative)

The mission's Phase B.1 asked where the worn-gear overlay art lives.
The answer, proven at the code level: **nowhere; DS1 has no
armour-overlay mechanism.** The inventory figure is a single base
sprite drawn once; equipping armour, weapons, or shields never
changes it. Key evidence (DS1 DSUN.EXE file offsets; DS2 mirror
checked):

- The screen family's art cache holds exactly 18 UI backdrops + the
  14 base figures (BMP 20000..20013, cache slots 18..31) + 14
  walk-cycle sets (preload at seg25 entry[27], file 0x72DC7). No
  other BMP id in the 20000-neighbourhood is referenced by any
  instruction or table in the image; the complete TOC enumeration of
  the neighbourhood (20014..20165) is chargen appearance portraits,
  UI plates, bars, and 32 same-silhouette scene plates, not gear.
- The figure draw (seg24 entry[29], file 0x6D52F) reads the
  character's figure index from charrec +0x18, adds 18, and blits
  one cached sprite: `[es:bx+0x18]; add ax,0x12; call 0x580:0x93`.
  Nothing draws after the base. Three sites total in DS1
  (0x6D52F family, 0x632BF, 0x65F9C); chargen preview draws at
  (0x32, 0x3C) = (50,60).
- The index is primary and persisted (chargen cycler seg16
  entry[33], file 0x63263: cycles the stored index, then derives
  race = (index>>1)+1 and gender = (index&1)+1 into the record; new
  characters start at index 0). Equivalent to the 09-20 formula
  `20000+(race-1)*2+(gender-1)` for all shipped combos except the
  tail: index 13 = race 8 = K'tarchek, and race 7 gender 2 has no
  art. Nothing rewrites the index after creation.
- Compositing is one transparent blit (index 0 skipped; the 09-20
  100.0% ground-truth match already proved it). Inventory figure
  anchor: board (81,49).
- Gear renders exclusively as item icons in the 14 paperdoll cells
  (APFM 11216-11229), via the per-cell icon drawer (seg24 cs:0x20EF)
  reading instance +0xC icons. The equip/unequip chain (0x6EF52,
  0x6F8B9, 0x5B8B9+) never writes the figure index. DS2 has the
  same architecture (figure slots at 0x61FF, draws with
  `[es:bx+0x10]; add ax,0x15`; the DSO names UpdateFigure /
  WearingArmor name the redraw and the mechanics, none dress a
  paperdoll).

Port consequence: the port already matches engine truth
(`inventory.gd` draws the base sprite and cell icons). Any
gear-on-figure visual would be an enhancement, not parity, and
should be flagged as such if ever wanted. The 09-20 "unproven link"
(index derivation) closes with the twist above.

## 7. Bestiary special-attack/defense enums resolved (Phase B.3 closed)

Both games' special-attack machinery is decoded from the consumer
code (the "enum candidates and are not shown" era is over; the
bestiary headers and object-formats.md rows now carry the
resolution):

- **DS1 combat+22 is the low byte of a WORD** that indexes a dword
  capability-bitmask table at EXE file 0x43850 (resident record 120,
  402 B). The AI gate (ovr5 0x57ba0) is `word != 0` plus the armed
  and global-suppressor tests; the probe (ovr6 entry[7], 0x5a90f)
  rolls 25% per round and walks 11 fixed bits, first match wins,
  firing the castable id through the router (0-based power-record
  indexes; bands in ovr28 stub21). The 11 probe specials, named via
  the power table + SPIN: FIREBALL (bit 26; the old DISPEL MAGIC
  label was off by one), two breath innates (20: 6d6, 31: 3d6), HOLD
  PERSON (30), DETONATE (6), INCREASE CONSTITUTION (12), poison
  innate (18), ranged innates (19, 22), a third breath (21), FEAR
  (29). Enum 41 = casting blocked (only Balkazar carries it);
  enums 128/129 index past the table into zero dwords and enum 19's
  bitmask is zero: all three inert. Elemental
  resistance/boost rows ride the same record at +0xa8/+0xd2/+0xda,
  addressed with the enum RAW as a byte offset: DS1 defense is
  folded into the enum record, not a separate field.
- **DS1 combat+23 is that word's high byte**, never read as a byte
  anywhere (every +0x17 byte hit is a stride-0x12 or item record);
  0 in all 291 rows; a nonzero value would push the table index out
  of range. The old "special_defense" label is corrected in
  object-formats.md.
- **DS2 combat+14 low** is a byte enum through ovr29 stub0's FOUR
  phase-keyed jump tables (A: 20 words phase 0; B: 18 words phase 1,
  incl. enum 18; C: 18 words behind the [0x420e] gate; D: 11 words
  for enums 10..20). The fire gate (stub3) is 1d4 == 4 (25%) plus a
  per-enum condition table: drakes/elementals (1-4, 6, 17) need the
  actor below half HP, the Verini poison (15) and the Mindflayer
  mind blast (12, at state 0) always fire, Tarrasque (13) never.
  stub4 then writes combat+0xe = 18 for enums 1-4 (second-phase
  marker). Per-row phase-0 specials are nameable (drake breaths,
  petrification touch, poison clouds, FIREBALL for Giant Skeletons).
- **DS2 combat+14 high (+15)** is a defense profile index: an
  18-word immunity table (damage -> 0; Rybochka 16 = 0xffff
  all-immune; elementals {3,4,5,12}) at EXE 0x4F588 plus a second
  halving table at 0x4F5AC consumed only for indices < 7; eight
  consumer sites census'd.
