## 1. DATA is the DS2 spell system's data file (layout proven, descriptor decode open)

The single biggest coverage gap is smaller than it looked and bigger
in content. The "1292 DATA chunks across 4 files" are 323 unique
chunks in one container shipped four times: DS2's RESOURCE.GFF
lineage (GOG CD `RESOURCE.GFF` and, byte-identical, `RESFLOP.GFF` in
the floppy 1.0, HotU, and cd10 trees; the three archive copies have
identical payload, the GOG 1.10 copy differs by exactly 5 bytes, see
below). 1292 = 4 x 323. No DS1 file carries DATA anywhere in the
corpus; DS1's RESOURCE.GFF instead carries RDAT (45 chunks), its
era's equivalent slot.

All four files carry DATA as a segmented type (runs `[(0,320),
(1000,3)]`, secondary table inside GFFI chunk 16); the per-chunk
(id, location, length) records have never been tabulated before
because format-coverage.py stops at the type list.

Layout (offsets cite `.games/ds2/RESOURCE.GFF`):

- Ids 0..319: exactly 320 records of exactly 73 bytes each, contiguous
  from 73960 (cd10/floppy base 73781; +179 in GOG 1.10).
- Record layout: bytes 0..31 binary descriptor, bytes 32..63 NUL-padded
  32-char long name, bytes 64..72 NUL-padded 9-char short name. All
  320 long names decode as clean ASCII, none empty.
- The names are the DS2 spell list: `ARMOR`, `BURNING HANDS`, `CHARM
  PERSON`, ... in near-alphabetical wizard-1 blocks, cleric and
  psionicist blocks (`PRAYER`, `IRON SKIN`, `ENHANCED STRENGTH`), and
  ids 269..319 = 51 `MONS269`..`MONS319` placeholders (summoned
  monsters carried as spells).
- Ids 1000..1002 are auxiliary tables appended after the interleaved
  TEXT id 1000 (the item/spell description list): id 1000 (320 B) =
  8 rows x 20 LE u16 monotonic-from-0 ramps (read as per-class
  level-up XP tables); id 1001 (576 B) = sparse flags with two
  self-similar halves; id 1002 (168 B) = 21 (u32, u32) pairs reading
  as (XP value, index) with lane 2 = 1 then 50..69.
- Size histogram across the kind: 73 x 320, 168 x 1, 320 x 1, 576 x 1.
  Nothing else exists in any of the four files.

The GOG 1.10 patch, exactly 5 bytes across all 323 chunks: id 155
(`PRAYER`) descriptor byte 1 `0x00 -> 0x14` (20), and id 1000 row 6
two u16 steps `14000 -> 24000`, `17000 -> 27000` (repairs a broken
+3000 progression). This is the official 1.10 RTPatch's data-table
work, visible at the byte level.

Open (documented as open, with confirm/refute tests):

- The 32-byte descriptor is undecoded. Byte 0 histogram {4:87, 5:98,
  6:81, 7:41, ...} smells like a school/level pair; byte 31 is
  bimodal 0xa0/0xa1 with a long tail. Tests: correlate against the
  shipped Cluebook's spell levels/schools; check byte 1 as an
  animation id (PRAYER gaining 20 in 1.10) by decoding SPIN/ICON 20/
  40/160 with image-extract.
- Id 1001's record shape (576 sparse bytes, no clean width; 576 =
  320 + 256 suggests per-spell scatter plus a second block). Test:
  align byte i to spell i for i < 320.
- Id 1002's index lane (1, 50..69) matches neither spell ids nor MONS
  ids. Test: xref the chunk id in DSUN.EXE's secondary-table reader.
- Whether id 1000's 8 rows map to the 8 classes in order is a guess
  until RDAT (DS1) or the engine reader is compared. Rows 3 and 5
  still hold non-monotonic steps in 1.10, so "clean progression" is
  not universal.

What this means for the port: the DS2 spell engine's data surface now
has a known address and shape (320 records + 3 tables), the same in
every release, so a Godot-side spell table can be generated from DATA
directly instead of hand-transcribing the cluebook. docs/spell-catalogue-ds2.md
gains a machine source.
