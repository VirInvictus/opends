# Port digs, 2026-09-21: the 15500/3020 dispatcher, the capability
# mask, and steal/give

All addresses are raw DSUN.EXE file offsets. The examine/interact
code lives in overlay segment 11 (cs:0 = file 0x5EC90, range
0x5EC90..0x5FD6F, verified with ovr-map). Resident and overlay
callees were resolved through the segtab procedure in
docs/overlay-formats.md 6. This dig closes the two questions left
open by port-digs-2026-09-20.md 3 and corrects one screen-flow
claim (8.3).

## 1. The 15500 buttons are not arrows (proven)

The engine's item-event callback is 0x5F2B7. Message type 2 (button
click) dispatches on the raw id:

    0x5F57B  mov bx, [bp+8]      ; button id
    0x5F57E  sub bx, 0x3BC5      ; id - 15301
    0x5F582  cmp bx, 7           ; ids 15301..15308
    0x5F58A  shl bx, 1
    0x5F58C  jmp cs:[bx+0xB69]   ; 8-entry table at file 0x5F7F9

Jump table (file 0x5F7F9), dumped byte-exact:

| id | position | handler | shares handler with |
|---|---|---|---|
| 15301 | x=13 (left) | 0x5F731 | 15306 TALK |
| 15302 | x=53 (right) | 0x5F754 | 15307 GIVE |
| 15303 | x=33 (middle) | 0x5F6BE | 15308 STEAL |
| 15304 | INFO | 0x5F591 | - |
| 15305 | no-op | 0x5F7E5 | - |

Triple corroboration: (a) the handlers are literally shared with the
interact strip's buttons; (b) both openers gate the pairs with the
same capability bits (15500 opener 0x5EFC5: test di,1 -> 15303,
test di,4 -> 15301, test di,0x10 -> 15302 at 0x5EFE5/0x5F00C/0x5F033;
interact opener 0x5F078: test di,1 -> 15308, test di,4 -> 15306,
test di,0x10 -> 15307 at 0x5F0AC/0x5F0D3/0x5F0FA); (c) the icon art
pairs are identical glyphs recoloured (15101~15105 mouth, 15102~15106
open hand, 15103~15107 hand+coin; 181/960 bytes differ, the 15500 set
sits on a different diamond colour). Left to right both windows read
talk, steal, give.

Which window opens is decided by the tracked-instance state byte at
[0x360]:0xC36+si*3: ==1 (item/object) -> 15500, ==2 (creature) ->
3020. The engine never opens 15500 on a party member's carried item.

Handler semantics:

- TALK 0x5F731: si = [0x844] (tracked instance saved at 0x5F234);
  close window; 0x90:0x1FF(si,1) then 8:0x21F([0x4979], si) starts
  the dialog. No item logic.
- GIVE 0x5F754: close; 0x530:0x6B([0x4979], si, 0) = file 0x62B86,
  the open-container/give flow (resolves the target's item template
  via 0x588:0x52 -> 0x74070, reads record +0x15/+0x1A, container
  check 0x62B63; for container items, IT1R+15 & 1, opens the give
  flow on the instance and clears mode [0x573D]). If the tracked
  thing is state 1 with IT1R+0xF & 8 (quick-item), also 0x4F0:0x57
  (0x5AFDC, the use/quick-item action).
- STEAL 0x5F6BE: see section 3.
- INFO 0x5F591: toggles [0x846] 0/1 and redraws. 1 draws the item
  plate via 0x640:0x2A(winptr, instance) (0x5F1EC-0x5F20B); 0 draws
  a 4-line description list (loop 0x5F610-0x5F68E, record stride
  0x47/0x3A). It does NOT open 15502 from here; screen-flow 8.3's
  "INFO opens 15502" is corrected. 15502's own opener (0x8AF59) is
  reached elsewhere (inventory flow), and 15502 still reads the
  instance index directly as described.

## 2. The capability mask source (proven; runtime structures named)

The opener wrapper (function entry 0x5ECD0, containing both openers)
builds di from two sources:

    0x5ECE1  push si; lcall 8:0x8AA      ; flags A: creature permissions
    0x5ECEB  call 0x5F8FD                ; flags B: item-side capabilities
    0x5ED11  and word [bp-2], 0x1D       ; flags A keep bits 1,4,0x10 (+8)
    0x5EF4F  or di, word [bp-2]          ; combined before the openers

Flags A (resident 8:0x8AA, file 0x967A): maps the instance to a
creature id, then ORs a bit per linked-list membership: head indices
at [0x377E]:+0xD (bit 1 steal), +0xF (bit 4 talk), +0x11 (bit 2),
+0x13 (bit 8), +0x15 (bit 0x10 give), +0x17 (bit 0x20). The walker
0x9720 follows 13-byte records via far pointer [0x4356]:[0x42CC]
(chain link +0xB, 0xFFFF terminates) and returns 1 when the current
creature id matches record +4 or +6 (0x9746-0x97A1). So steal/talk/
give availability is per-creature PERMISSION LISTS populated at
runtime; the populating code was not traced (region/script load is
the likely writer).

Flags B (0x5F8FD, state-1 items only): bit 1 takeable (IT1R+8 & 0x20
clear, 0x5F982-0x5F989; 0x20 is one of the too-big-to-carry bits);
bit 0x10 container give (IT1R+15 & 1, decided by 0x530:0x89 of
rec32+0x11, and a nonzero return REPLACES the whole mask with 0x10,
0x5F9DD-0x5F9FB); bit 0x40 quick-item (IT1R+15 & 8); helper 0x5F821
adds bit 8 or bit 0x80. State-2 creatures get bit 8 unconditionally
(0x5FA26). The wrapper short-circuits single-capability cases:
(di|flags)==4 -> talk with no window (0x5EF00-0x5EF1D); di==0x10 ->
give path; ==0x40 -> quick-item use; item category 1399 -> auto-take
(0x5EEA8-0x5EEE4).

## 3. Steal and give paths (transfer proven; no thief roll found)

STEAL 0x5F6BE branches on the cursor-held-item gate 0x588:0x43 (file
0x73530: cmp word [0x17A0], 0xFFFF; the same gate as the 13500 SELL
button):

- Holding an item -> 0x588:0x75 = 0x73F90: if the target is a party
  member (state 2, 0 <= si < 4) -> 0x73C40 GiveHeldToChar (the
  documented TOO BIG TO CARRY / TOO MANY ITEMS checks); if state 1
  (ground/container item) -> place worker 0x73AA8 then take worker
  0x73725.
- Empty hand -> 0x588:0x70 = 0x73725, the take verb: enumerates the
  target's items via 0xA0:0x1A2D (0x20ECD, tracked-instance scan)
  into the 64x10-byte list at [0x380], selects an entry into the
  held slot [0x17A0] (0x73855); coin-category results print
  "YOU FIND %u$" (format ds:0x1D8A = 0x4A6EA) through the rules
  message service 0x4D0:0x2A.

No dice roll, skill stat read, or percentile compare exists anywhere
on this static path (0x5F6BE, 0x73530, 0x73725, 0x73AA8, 0x73F90);
the only rules call, 0xB8:0x909, is derived stats. The gating is the
section-2 steal permission list. Working verdict: DS1's steal is
permission-gated, not rolled; a hidden roll inside the enumeration
service cannot be fully excluded but has no static evidence.

GIVE: see the 0x5F754 handler note in section 1. Direct
member-to-member handoff is the 0x73C40 path reached through the
steal-position button while holding an item, not through GIVE.

## 4. What this means for the port

- examine_strip.gd's mapping (15301 back, 15302/15303 forward,
  15304 -> 15502) is an invention end to end; the engine cycles
  nothing and opens nothing from these buttons. The port opens
  15500 in a context the engine never uses (a member's carried
  item), so any mapping there is a port affordance by definition.
  A rebuild to engine truth means opening the strip on world items
  with the capability mask, which duplicates the interact strip's
  role for the item case. Decision pending with Brandon.
- Steal/give in the demo: the capability mask is per-creature
  runtime permission lists, so a demo entity offers steal/give only
  if the region scripts put it on those lists. Implementing the
  buttons is a transfer-path job (0x73725 take / 0x73C40 handoff),
  not a skill-check job; there is no roll to port.
